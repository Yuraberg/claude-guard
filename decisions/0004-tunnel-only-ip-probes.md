# 0004. Выходной IP мерим только через адреса, идущие в туннель

**Дата:** 04.10.2026

> **Устарело:** список источников заменён решением
> [0007](0007-probe-chain.md) — теперь Cloudflare trace (у `ipinfo.io` бесплатный тариф
> упирается в HTTP 429 и давал ложные отказы). Правило «мерить только то, что идёт в туннель»
> остаётся в силе.

## Решение

Для «какой IP видит Anthropic» используются только `https://ipinfo.io/ip` и
`https://ifconfig.co/ip` (две попытки с паузой 2 с). `api.ipify.org`,
`checkip.amazonaws.com` не используются — несмотря на то, что они отдают IP простым текстом.

## Почему

На рабочей машине сплит-туннель: часть адресов уходит через `tun0` (США), часть —
напрямую. Замер это показал явно:

```
https://ipinfo.io/ip             → 203.0.113.10    (выход VPN)
https://ifconfig.co/ip           → 203.0.113.10    (выход VPN)
https://api.ipify.org            → 198.51.100.23   (домашний РФ-адрес, напрямую)
https://checkip.amazonaws.com    → 198.51.100.23   (домашний РФ-адрес, напрямую)
```

(адреса — из документационных диапазонов RFC 5737, реальные заменены)

Если такие адреса попали бы в список источников как «первые ответившие», проверка решала
бы, что выход — домашний РФ-адрес: это либо вечный отказ (fail-closed сработал бы
впустую), либо — хуже — пометка «плохим» не того IP в `web-blocked-ips`, и реальный
выход остаётся неизвестным.

## Следствия

- Список источников сознательно короткий; при недоступности обоих проверка считается
  непройденной (fail-closed), а не подменяется «похожим» сервисом.
- Вторая попытка с паузой 2 с добавлена после наблюдения транзиентно пустой пробы: без неё
  страж впустую отказывал, а сторож не помечал плохой выход.
- Правило для будущих правок: добавляя любой источник IP/страны, сначала проверить, идёт
  ли он через туннель, а не напрямую.
